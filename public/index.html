OPERATING MODEL

How Ephemeral Secret Vault Works

An end-to-end zero-trace architecture from client transmission to disk zero-overwriting.

01

Payload Submission

You enter sensitive credentials, confidential API keys, or attach any file (documents, images, or Python scripts like surya.py) up to 10 MB.

02

In-Memory AES-256-GCM Encryption

The server immediately encrypts the payload in memory with a fresh 12-byte IV and 16-byte authentication tag. No plaintext ever touches storage or logs.

03

Dual Delivery Distribution

Share via an unguessable 12-character URL (with 1-click WhatsApp, Slack, Teams, and QR Code) or download an offline self-extracting .html vault package.

04

Single-Use Atomic Destruction

The recipient opens the link or file and clicks "Reveal & Destroy". Upon decryption, the SQLite database row is overwritten with zeros using PRAGMA secure_delete = ON;.

SECURITY FOUNDATION

Engineered for Zero-Trust Environments

Six foundational protections implemented directly in our cryptographic and storage layers.

1. AES-256-GCM

Authenticated hardware-grade encryption. Plaintext is never stored or written unencrypted.

2. Unique IV

Fresh 12-byte cryptographic initialization vector generated for every individual secret.

3. Burn After Reading

Automatic hard destruction after allowed views are consumed. Records are zero-overwritten.

4. Scraper Defense

GET requests from bots (Slack, WhatsApp, Discord) receive a safe static landing shell with 0 DB burns.

5. Atomic Reads

Single-transaction SQLite updates prevent double-read concurrency race conditions.

6. Automatic Cleanup

Autonomous background sweeper purges expired secrets and checkpoints the WAL database.

01

Encrypted at Rest

Your secret is never stored as readable plaintext. Ciphertext, salt, IV, and auth tag are isolated in a hardened SQLite WAL database with cryptographic zero-delete.

02

Human-Controlled Reveal

Opening the link loads a safe landing page. The plaintext secret is only decrypted upon an explicit, authenticated POST request initiated by a human recipient.

03

Automatic Destruction

The secret becomes permanently unavailable after successful reveal or expiration. Deleted blocks are zero-overwritten in memory and storage with no retention.

Architecture & Operating Model

1. In-Memory Encryption

When you submit a secret note or upload a file, it is immediately encrypted in server memory with AES-256-GCM. Only ciphertext, a 12-byte IV, and a 16-byte authentication tag are persisted in SQLite.

2. Secure Distribution

A 12-character non-guessable random URL is generated. You can share it directly via 1-click integrations for WhatsApp, Slack, MS Teams, Discord, or Email.

3. Atomic Single-Use Reveal

Recipients view a safe pre-reveal landing page. Clicking "Reveal & Destroy Secret" issues an authenticated POST request that decrypts the secret and immediately deletes the database row.

4. Hardware-Level Zero Overwrite

The database runs with PRAGMA secure_delete = ON; ensuring deleted table cells are physically overwritten with zeros rather than merely marked as free.

Security Architecture & Cryptographic Proof

Authenticated Cipher

We use AES-256-GCM (Galois/Counter Mode), guaranteeing both confidentiality and tamper detection. Any bit manipulation immediately fails decryption.

Zero Plaintext at Rest

Plaintext secrets and uploaded files never touch the hard drive unencrypted. Even SQLite WAL write-ahead logs contain only encrypted ciphertext bytes.

Scraper & Crawler Shielding

Automated link preview bots (Slackbot, Twitterbot, WhatsApp, Facebook, Discord) receive an isolated static preview shell. The secret is never decrypted by crawlers.

Zero-Knowledge Passphrase

If you set a passphrase, the key is derived using PBKDF2 with 100,000 iterations and a cryptographically secure per-secret salt.

Frequently Asked Questions

Can a burned secret ever be recovered?

No. When a secret burns, its database row is hard-deleted from SQLite and zero-overwritten. There are no backups, logs, or caches containing the decrypted payload.

What happens if the recipient never opens the link?

Our background sweeper service periodically purges all secrets that have passed their TTL expiration date. The data is wiped automatically.

Does pasting into Slack or WhatsApp trigger accidental destruction?

No. Automated bot requests for unfurling / link previews are served a harmless static shell. Destruction only occurs upon an authenticated human POST action.
