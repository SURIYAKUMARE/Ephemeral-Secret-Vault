How Ephemeral Vaulting Works

From creation to permanent cryptographic destruction: understand what happens at each stage of your secret's lifecycle.

1

Step 1: Input Secret Content or File

You provide sensitive text (API keys, passwords, database URLs, notes) or upload a confidential file (code scripts, certificates, PDFs, images up to 10 MB). You configure an expiration duration (from 5 minutes up to 7 days) and view allowance (1 to 5 views).

2

Step 2: Server-Side In-Memory AES-256-GCM Encryption

Upon receipt via HTTPS TLS 1.3, the secret is immediately encrypted using AES-256-GCM with a newly generated cryptographically random 96-bit IV. The plaintext is zeroized from heap memory and never touches disk unencrypted.

3

Step 3: Unique Vault Link Generation

The vault generates a non-sequential, random 64-bit hexadecimal Vault ID. The Vault ID is an opaque pointer that contains zero secret data and zero encryption keys.

4

Step 4: Safe Distribution (WhatsApp, Gmail, Outlook, Slack)

You share the link via WhatsApp, email, Slack, or any platform. The actual secret NEVER enters message drafts or cloud backups. When preview crawlers (Slackbot, Twitterbot, etc.) inspect the link, they receive a dummy static preview shell with zero decrypt operations.

5

Step 5: Two-Step Authorized Reveal Flow

When the recipient opens the link, the page loads with zero plaintext. When they click "Reveal Secret", the frontend requests a single-use authorization token from the backend. The backend validates policy, decrements views, decrypts in memory, and returns the payload.

6

Step 6: Cryptographic Shredding & Zero Retention

Once the view limit is reached or the expiration time elapses, the database record is atomically deleted. Memory buffers are overwritten with zeros. Any subsequent attempts to view the URL return 404 or redirect to the burned page.
